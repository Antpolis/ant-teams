# Write for the Audience

## Trigger

Apply when creating or substantially revising a document, or when a reader's understanding or decision depends on its clarity. Match collaboration and verification effort to the document's importance and the user's preferred working style.

## Rule

Shape the document around its readers, purpose, and intended action. Gather relevant context, distinguish evidence from assumptions, and check whether a reader can understand and use the result without relying on the author's unstated knowledge. Collaborate as needed without forcing a formal interview or review process on every edit.

## Apply

- Establish the document's audience, purpose, expected decision or action, applicable constraints, and existing template from available context. Ask focused questions only when consequential information cannot be established safely.
- Organize the content so readers can find the outcome, rationale, relevant evidence, limitations, and next steps. Use concrete language and preserve material nuance; link accessible supporting sources without assuming a link alone explains the decision.
- For collaborative work, present a draft or focused alternatives, incorporate the user's corrections, and make unresolved choices visible. Let the user choose a freeform approach when appropriate.
- Check the result against its purpose and the actual source material. For consequential or ambiguous documents, use an independent reader or an equivalent fresh-context review when practical; report when that check was not possible rather than claiming it happened.
- Follow applicable project documentation routing, templates, format conventions, and ownership. Use `principle-concise-actionable-communication` for concise messages and `principle-respect-project-constraints` where project rules apply.

## Boundaries and examples

- For a technical decision record, explain the decision, its rationale, meaningful alternatives, and consequences so a future maintainer can understand it without the original discussion.
- Fixing a typo in an existing note does not require a structured interview, a new document, or independent reader testing.
- Do not invent evidence, disclose sensitive information, impose a particular storage location on ordinary work, or start a managed workflow merely because documentation is requested.
